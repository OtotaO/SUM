    What is and is not checked

    Literal evidence, not a judgment. Notes name the passages or text searched. Word matching lowercases text, normalizes apostrophes and ignores gaps between words; it does not establish meaning or movement. Invisible controls are displayed as Unicode labels in notes, while original texts and exports stay unchanged. Decisions are exported unsigned.

    • ‸ the rewrite has nothing here

    Checked here

    • The words and characters that differ within each passage pair, marked in place up to a stated display limit
    • Normalized word matches within the passage or whole-text scope named in each note; character notes identify marked characters only
    • Fixed lists and patterns for numbers, dates, durations, negation and modal words, condition and exception markers, and capitalized words; these labels do not determine grammar or meaning
    • Passage order and text outside passages, including before the first and after the last passage
    • Lengths and span positions in UTF-16 code units, not visible-character counts

    Not checked

    • Meaning, paraphrase or entailment
    • Whether either text is accurate
    • Whether a difference matters to you
    • Whether a word the lists recognise really is a name, date or number
    • Word by word, a passage pair with very many differences: it is shown whole
    • Who wrote or approved either text

      The packet is one unsigned JSON file. The person you send it to can recompute the hashes, the passage spans and this comparison in their own browser.

        What is this
          
        Each claim (subject, predicate, object) is mapped to a prime via SHA-256(axiom_key) → seed → nextprime(seed). The state integer is the LCM of every prime. Two states merge by taking their LCM, and state % prime == 0 answers “does this state contain claim X?”. It is arithmetic over the extracted claims, not a check of the original.
        
        
        
        
        Unsigned in-browser mint: the bundle carries signature: "unsigned:v0". Anyone can recheck that the state integer matches the tome. For HMAC or Ed25519 signatures, run sum attest --signing-key … (see DID_SETUP.md).

        4Measure with a local semantic judgeA per-document measurement under a named local model, from the command line.runs on your machine
    
        
      
        The comparison above is literal. For a separate per-document proxy measurement under a named local judge, run:
        
      
        pip install "sum-engine[research,judge]"
sum meaning-diff source.txt rewrite.txt --scorer nli
        
      
        This is a per-document measurement under a named judge, not a corpus bound (a sum.meaning_risk_receipt.v1 over a corpus states a bound under its sampling assumptions). Integrators check any SUM receipt offline with few dependencies: pip install "sum-engine[verify]", then python -m sum_verify. See the meaning-loss frontier.
        
    
        

  
        5Verify a claim bundleRecompute a bundle’s state integer from its text and check an Ed25519 signature.runs in this browser
    
        
      
        Paste a SUM bundle JSON. Two checks run here: structural, which recomputes the state integer from the canonical tome and compares it with the claimed one, and Ed25519, which checks the public_signature against the bundle’s public_key with the browser’s own SubtleCrypto (Chrome 113+, Firefox 129+, Safari 17+). A key or signature that cannot be decoded fails the check. HMAC (shared-secret) signatures need sum verify --signing-key …. A passing check shows which key signed the bundle, not who holds that key or whether the claims are true.
        
      
      
      
        
    
        

  
        6Verify a meaning receiptCheck the signature, schema and disclosure of a sum.meaning_risk_receipt.v1 (Stage A).runs in this browser
    
        
      
        Paste a sum.meaning_risk_receipt.v1 (or sum.perspective_risk_receipt.v1) and its issuer JWKS. This runs Stage A here: the Ed25519 signature, the schema, and the required meaning-loss disclosure, the same checks the Python sum_verify SDK and the Node verifier run. Stage B (replaying the bound) stays in Python (python -m sum_verify --demo). There is no live meaning-issuing key, so paste or load a JWKS rather than fetching one. A clean result is a cryptographic fact, not a measurement of meaning.
